    ```python

                Index("ix_msg_recv_unread", "receiver_id", "read_at")
    ```

  - 迁移注意：`CREATE INDEX` 对 SQLite 是"加锁重写"，消息表大时耗时可观，建议分批/低峰执行并观察 `journal`。

### B-06 请求限流可被绕过（信任 `X-Forwarded-For`）+ 单进程内存态 + 聊天/群聊无发送限流
- **问题描述与复现**：
  - `rate_limit.py:29-33` `_client_ip()` **无条件信任** `X-Forwarded-For` 首段，未做可信代理校验。攻击者每次请求伪造不同 `X-Forwarded-For` 即可获得无限配额，绕过注册/登录（`RATE_AUTH_PER_MIN=10`）与 AI 限流。
    复现：`for i in $(seq 1 100); do curl -H "X-Forwarded-For: 1.2.3.$i" -d '{"username":"x","password":"y"}' .../api/auth/login; done` → 100 次均不被 429。
  - `rate_limit.py:25` `_buckets` 为进程内 `defaultdict(deque)`，`config.py:23` 注释已声明"单进程内存实现，多进程需换 Redis"。多 worker（如 `uvicorn --workers N`）下各 worker 独立计数 → 实际阈值放大 N 倍；且 `_buckets` 的 **key 永不删除**（只 pop 队列元素），不同 IP 持续访问会令字典无界增长（内存泄漏，见 B-21）。
  - **聊天发送无任何限流**：`chat.py:90` `send_message`、`groups.py:312` `send_group_message`、`ws.py:41` `_handle_msg` 均无 `rate_limit` 依赖 → 单个好友/成员可高频刷消息（落库 + 逐条 WS 广播给全体群成员）。
  复现：登录后循环 `POST /api/chat/{peer}/messages`、或 `POST /api/groups/{gid}/messages`，无 429。
- **影响范围**：全站限流语义失效；AI（付费额度）被刷；聊天/群聊消息灌爆数据库并向全体群成员广播形成放大。
- **严重程度**：**严重**。理由：限流是防滥用/防刷的唯一边界，其可被单头部绕过并叠加"发送无限流"，直接关联成本与可用性。
- **根因分析**：`rate_limit.py:29-33`（XFF 直信）、`rate_limit.py:25`（内存态）；`chat.py:90`、`groups.py:312`、`ws.py:41`（缺依赖）。
- **具体修复方案**：
  1. `_client_ip()` 改为**仅在受信反代**场景读 XFF：由配置项 `TRUSTED_PROXIES` 控制，或统一取 `request.client.host`（本机 nginx 反代时应固定取 `request.client.host` 并让 nginx 覆盖 XFF）。改 `rate_limit.py:29-33`。
  2. 为 `send_message`/`send_group_message`/WS `_handle_msg` 增加限流（如 `rate_limit("chat")`，新分组 `RATE_CHAT_PER_MIN`，建议 60~120/min）；WS 内改为对同一连接做本地窗口计数（`ws.py:41` 入口）。
  3. 多进程部署前置共享限流（Redis）或强制单 worker（并在文档/启动脚本固定 `--workers 1`，与 `wsmanager` 单进程前提一致）。
  4. `_buckets` 定期清理空队列 key（见 B-21）。
- **优化建议**：登录接口额外加"失败次数按账号"锁定（见 B-17）。

### B-07 SQLite 外键未启用（FK 级联失效 → 孤儿行）+ 无 WAL/journal 调优（并发写 `database is locked`）
- **问题描述与复现**：
  - `database.py:10` `create_engine(DB_URL, connect_args={"check_same_thread": False})` 未注册 `PRAGMA foreign_keys=ON`。实测：`tools/qa/r73/verify_report.txt` 第 1 行 `foreign_keys=0`。SQLite 默认**不**启用 FK → 所有 `ondelete="CASCADE"`（`database.py:74/100/110/119/136/151/165/175/190/202/218/231/243/254/262/274/289/300/312/322/334/343`）在运行期**不生效**。代码仅在 `groups.py:399-402`、`moments.py:299-301` 等少数处显式手工清理子表；一旦有遗漏（如未来新增删除路径、或直接 SQL 删除），即产生孤儿行并破坏计数一致性。
    复现：手动 `DELETE FROM notes WHERE id=?` 后 `SELECT count(*) FROM comments WHERE note_id=?` → 仍 >0（孤儿）。
  - 实测 `journal_mode=delete`（非 WAL）：读事务阻塞写事务。`busy_timeout=5000`（5s 默认）。高并发写（点赞/发消息/写通知）时易现 `sqlite3.OperationalError: database is locked`，且**未被捕获** → 500（如 `social.py:50`、`chat.py:47`、`groups.py:325` 的 `db.commit()` 均无 `try/except`）。
- **影响范围**：数据一致性（孤儿行 / 计数漂移）；并发写高峰期接口 500；`likes_count/comments_count/replies_count` 冗余计数可能与真实行数不一致。
- **严重程度**：**严重**。理由：并发与控制台均会命中，且属"静默数据腐化"。
- **根因分析**：`database.py:10`（缺 pragma 事件监听）；`database.py:11/490-495`（无 busy_timeout/WAL 设置）。
- **具体修复方案**：
  1. 在 `database.py:10` 之后注册连接初始化：
     ```python
     from sqlalchemy import event
     @event.listens_for(engine, "connect")
     def _sqlite_pragma(dbapi_conn, _):
         cur = dbapi_conn.cursor()
         cur.execute("PRAGMA foreign_keys=ON")
         cur.execute("PRAGMA journal_mode=WAL")   # 读写并发：读不阻塞写
         cur.execute("PRAGMA busy_timeout=5000")
         cur.execute("PRAGMA synchronous=NORMAL")
         cur.close()
     ```

- **根因分析**：`security.py:51`、`wsmanager.py:35`、`ai.py:173`、**`feedback_public.py:53-62`（损坏即返回 `[]` 且随后被 `_save_all` 覆盖）**。
- **具体修复方案**：
  1. `_load_all` 遇损坏时应**抛错或备份后改名**（如 `feedback.json.corrupt-{ts}`），绝不返回空列表继续覆盖。改 `feedback_public.py:53-62`。
  2. 其余静默处加 `logging.debug/warning`（保留"不影响主流程"的语义）。
- **优化建议**：接入结构化日志与告警。

## 建议（Suggestion）

### B-20 密码哈希策略：PBKDF2 迭代 12 万偏低；校验用非常量时间比较
- **问题描述与复现**：`security.py:20` `_ITERATIONS = 120_000`（OWASP 对 PBKDF2-HMAC-SHA256 建议 ≥600k）；`security.py:68` `return dk.hex() == dk_hex` 为非恒定时间比较（理论上可被计时侧信道）。
- **影响范围**：口令离线破解成本；侧信道。
- **严重程度**：**建议**。
- **根因分析**：`security.py:20/62-70`。
- **具体修复方案**：迭代提至 600k（`security.py:20`）——**注意**：存量哈希前缀已带迭代数（`security.py:59` 写入 `pbkdf2${iters}$...`），`verify_password` 按存储的 iters 校验（`security.py:64-67`），故提升不影响老用户登录（老哈希仍按其自带 iters 校验），属可平滑升级；比较改用 `hmac.compare_digest`（`security.py:68`）。
- **优化建议**：新用户注册/改密用新迭代数，老用户在下次登录成功后**顺手重哈希**。

### B-21 进程内状态字典无清理（内存随维度无界增长）
- **问题描述与复现**：`security.py:28` `_last_seen_cache`（按 user_id，量级=用户数，尚可）、`rate_limit.py:25` `_buckets`（**key=分组:IP，永不删除**，IP 维度无界）、`feedback.py:25-26` `_ten_min_buckets/_day_buckets`（按 uid，量级=用户数）。长跑进程内存只增不减。
- **影响范围**：服务端常驻内存。
- **严重程度**：**建议**。
- **根因分析**：上述字典仅在取值/追加时清理队列元素，未删除 key。
- **具体修复方案**：定期（如每 N 次调用或后台任务）清理空队列 key；或改用带 TTL 的 LRU（`cachetools.TTLCache`）。
- **优化建议**：限流迁移 Redis 时一并解决（B-06）。

### B-22 `建表SQL.sql` 与 ORM 漂移（缺表缺列、索引不生效）→ 误导运维/评审
- **问题描述与复现**：`建表SQL.sql` 仅含部分表（users/notes/likes/favorites/comments/notifications/chat_groups/chat_group_members/moments/moment_likes/moment_comments/feedbacks/study_logs/friend_remarks），**缺** `friends、friend_requests、user_blocks、messages、board_messages、board_likes、board_replies、ai_usage、ai_logs` 与 `users` 大批列（bio/gender/.../is_admin/last_seen_at 等，`database.py:35-65`）。文件顶部称"首次启动会自动按本结构建表"，实际运行期只跑 `create_all`（不含该文件的 `CREATE INDEX`，见 B-04）。
- **影响范围**：人工核对/手工初始化/评审依据失真。
- **严重程度**：**建议**。
- **根因分析**：`建表SQL.sql` 由人工维护、与 `database.py` 模型不同步。
- **具体修复方案**：改由 SQLAlchemy 生成 DDL（`sqlalchemy.schema.CreateTable`）自动导出，或加 CI 断言"该文件含全部表/Index"。若保留文件，补全缺失表并把 `CREATE INDEX` 纳入 `init_db()`。
- **优化建议**：引入 Alembic 管理迁移（当前 `_upgrade_legacy_schema` 手写 ALTER，`database.py:402-482`，可长期演进为 alembic `versions`）。

### B-23 WebSocket：token 走 query 参数 + 无发送限流 + sender 可能为 None
- **问题描述与复现**：
  - `ws.py:32` `ws.query_params.get("token")` —— 令牌出现在 URL，易被访问日志/代理记录。
  - `ws.py:41-61` `_handle_msg` 无速率限制（见 B-06）。
  - `ws.py:58` `store_and_deliver(db, db.get(User, uid), ...)`：若用户已注销，`db.get` 返回 None → `store_and_deliver` 内 `sender.id` 抛 `AttributeError`；该异常未被 `ws.py:107` 的 `except (WebSocketDisconnect, TimeoutError)` 捕获 → 连接异常中断。
- **影响范围**：WS 安全与健壮性。
- **严重程度**：**建议**。
- **根因分析**：`ws.py:32/41-61`。
- **具体修复方案**：令牌改从首帧/子协议或 `Sec-WebSocket-Protocol` 传递；`_handle_msg` 加限流；`ws.py:58` 对 `db.get(User, uid)` 为 None 时回 error 并 return。

### B-24 历史泄露事故遗留：确认密钥轮换与历史清除
- **问题描述与复现**：`.gitignore:35` 自述"2026-09-11 发现 `server/data.db` 与 `server/backups/` 曾被推上公开仓库"。若彼时仓库内含真实 `JWT_SECRET`/AI API Key（`.env` 现已被忽略，但历史提交可能含敏感数据），需确认已轮换。
- **影响范围**：历史凭证。
- **严重程度**：**建议（待确认）**。
- **根因分析**：`.gitignore:35-41`。
- **待确认验证**：`git log --all --full-history -- server/data.db server/backups server/.env` 是否存在历史提交；若存在，检查其中是否含密钥。
- **具体修复方案**：轮换 `JWT_SECRET`、各家 `*_API_KEY`、`FEEDBACK_ADMIN_KEY`；必要时用 `git filter-repo` 清理历史并强推（需团队协调）。
