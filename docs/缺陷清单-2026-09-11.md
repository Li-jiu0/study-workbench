## A. 用户点名 Bug 复核（6 类）

### A-① 「群聊弹窗跑到右上角」 —— ❌ 不成立（多视口实测均居中，且原假设的根因链条是错的）

- **现象（用户描述）**：点「👥 群聊」后弹层跑到右上角。
- **复现步骤**：打开 `私聊.html`（注入合法形态登录态）→ 真实点击 `button[onclick*=imOpenGroupCreator]` → 读取 `#imGroupModal` 与 `.im-modal` 的 `getBoundingClientRect()` + 全祖先 computedStyle。
- **证据（实测，非推测）**：

  | 视口 | overlay 实测 | 弹窗中心 vs 视口中心 |
  |---|---|---|
  | 1440×900 | 1440×900 @ (0,0) | cx 720/720，cy 450/450 ✅ |
  | 1280×800 | 1280×800 @ (0,0) | cx 640/640，cy 400/400 ✅ |
  | 1024×480 | 1024×480 @ (0,0) | cx 512/512，cy 240/240 ✅ |
  | 390×844 | 390×844 @ (0,0) | cx 195/195，cy 432/432 ✅ |
  | 375×667 / 360×640 | 全屏 @ (0,0) | 完全居中 ✅ |

  computed `position:fixed`、`top:0;left:0`，z-index 9998。
- **根因判断（对任务给出的假设给出确定结论）**：**「`.im-overlay` 因祖先 `.page` 带 animation+transform 而 lost containing block」这一假设不成立，两处前提都不对**：
  1. `#imGroupModal` **根本不是 `.page` 的后代**——它在 `私聊.html:199-205`，是 `.app`（58 行）的直接子级、`.main`（118 行已闭合）的**兄弟节点**；`.page#page-im` 在 78-117 行已闭合。实测 `o.closest('.page') === null`。
  2. 实测祖先链只有 `DIV.app → BODY.theme-home → HTML`，三者 computed `transform:none / animationName:none / filter:none / willChange:auto / contain:none`（`.app` 仅 `position:relative`，见 common.css:85）。`position:fixed` 的 containing block 仍是视口，因此任何「lost containing block」都不会发生。
  3. `.page` 的 animation（common.css:441 `fadeInUp`、1721 `fadeIn`，关键帧 446/1722 确有 `translateY`）即便触发，也只作用于 `.page` 自身，与本弹层无关；且动画无 `fill-mode`，结束后 transform 回到 `none`。
- **严重度**：信息级（无法复现的"缺陷"）。
- **建议修法**：**无需修定位**。可按 PRD-A1 做纯增强：`.im-overlay` 增加 `padding:env(safe-area-inset-*)`、`.im-modal` 增加 `margin:auto; max-height:calc(100vh - 40px)`，并补 `Esc` 关闭（当前仅支持点遮罩/✕ 关闭）。

### A-② 「群聊多选列表点头像触发大图预览」 —— ❌ 不成立（多选列表头像没有任何预览绑定）

- **复现步骤**：同上打开弹层 → 检查 `.im-glist` 行内 HTML 与 onclick → 用 `document.elementFromPoint(头像中心)` 真实点击头像 → 对比 DOM 节点数/新增 fixed 层/`window.open` 调用/URL/勾选态。
- **证据**：
  - 渲染源 `chat-local.js:950-956`（以及 980-992 的过滤分支）：行是 `<div class="im-sess" onclick="window.imToggleGroupMember(<id>)">`，头像是 `<div class="im-av">' + renderAvatar(...) + '</div>`，**头像 `div.im-av` 与其内层 `<img>` 都没有 onclick**（`renderAvatar` 定义在 chat-local.js:23-34，只产出 `<span>` 或无绑定的 `<img>`）。
  - 实测：`avatarOnclick=""`、`avatarInnerOnclick=""`、`rowOnclick="window.imToggleGroupMember(9001)"`；点击后 `nodeDelta=2`（仅勾选圈状态变化）、`selectedAfter=1`（该好友被勾选）、`fixedLayers` 只有弹窗本身、`window.open` 调用 0 次、URL 不变。
  - 全站检索 `lightbox / viewer / showImage / viewImage / openImage / 大图 / 图片预览 / new Image(` （assets + 根目录 html，排除备份/依赖）——**聊天链路 0 命中**；仅有命中在 PPT 文案、`动态.html` 的【后续扩展点：动态图片 lightbox】空注释、`app.js:5343`（头像上传压缩，无关）。
- **根因判断**：多选列表头像点击的唯一效果就是**冒泡到行 → 切换勾选**，这是预期行为；不存在"大图预览"。
- **真正的头像误触来源（很可能才是用户感知到的现象）**：**会话列表**与**好友列表**的头像**显式绑定了 `openUserHome`**——
  - 会话列表：`chat-local.js:178-182`（`avClick = 'event.stopPropagation();openUserHome(<serverId>)'`）
  - 好友列表：`chat-local.js:261-262`（`<img ... onclick="event.stopPropagation();openUserHome(...)">`）
  - `openUserHome`（`api.js:261-264`）→ `location.href='个人中心.html?user=<id>'`，对方主页头部是 72px 大头像（`.profile-avatar-lg`）。
  - 即：**想点行进会话却点中头像 → 跳到对方主页**，视觉上像"点了头像弹出别的东西"。
- **严重度**：中（交互误触，A2 的真实落点）。
- **建议修法**：按 PRD-A2 把"头像"与"行"的点击区分离——多选列表保持现状（只切换勾选）；会话/好友列表头像改为「查看资料」的显式次级动作或取消绑定，行点击才进会话。

- **证据**：

  - 此外"加好友"还有第三种形态：私聊页搜索结果里的行内 `加好友` 按钮（`chat-local.js:793` `imAddServerFriend`）与 他人主页的 `👤 加为好友`（`api.js:201`）。同一动作三种呈现。
- **严重度**：低（一致性/美观，不影响功能）。

### A-④ 「已是好友仍显示『添加好友』、且无『删除好友』」 —— ✅ 成立（真 Bug，且为上轮 P0-5 的回归级缺陷）

- **复现步骤**：mock `GET /api/users/9001`（返回 `isFriend:true`）与 `GET /api/friends`（返回 `{items:[{id:9001,…}]}`，与真实后端返回结构一致）→ 打开 `个人中心.html?user=9001` → 读取渲染出的按钮。
- **实测结果**：`buttons = ["← 回我的主页", "👤 加为好友"]`，`showsAdd=true`、`showsDelete=false`、`showsMsg=false`（截图 `.qa/bug4_userhome_buttons.png`）。**即使接口已明确返回 `isFriend:true`，页面仍显示「加为好友」，且永远不会出现「发私信 / 删除好友」。**
- **证据 / 根因（确定）**：`assets/api.js:191-193`
  ```js
  var friends = await api('/api/friends');
  isFriend = friends.some(function(f) { return f.user && f.user.id === userId; });
  ```
  两处错误叠加：
  1. 后端 `GET /api/friends` 返回的是 **`{"items":[…],"total":n}`**（`server/routers/friends.py:145-158`），**不是数组**；对对象调用 `.some` 抛 `TypeError`，被 `try{}catch(e){}` 吞掉 → `isFriend` 恒为 `false`。
  2. 即便把 `items` 取出来，元素也是**平铺的 peer brief**（`{_peer_brief(u), "since":…}`），**没有 `.user` 嵌套**，`f.user` 恒为 `undefined`。
  3. 后端 `GET /api/users/{id}` 其实**已经返回了 `isFriend`**（`server/routers/users.py:150`），前端 `renderUserHome` 完全没消费它——这是上轮 T1 交付后前端未接线的遗漏。
- **连带影响**：`api.js:197-199` 的 `💬 发私信` / `🗑 删除好友` 分支永不可达 → 用户看到的正是"无删除好友入口"。后端 `DELETE /api/friends/{peer_id}`（`friends.py:161-169`）与前端 `removeFriend()`（`api.js:250-257`）都已就绪，只是被这个布尔判断卡死。
- **严重度**：**高**（好友关系判断失效 + 好友管理入口不可用，用户点名）。
- **建议修法（一处即可修好）**：`renderUserHome` 直接改用接口已返回的字段：
  ```js
  var isFriend = !!u.isFriend;   // users.py 已返回
  ```
  或保守写法 `var list = (friends && friends.items) || []; var isFriend = list.some(f => f.id === userId);`。同时按 PRD-A4/A5：已好友时渲染「发消息 + 删除好友（二次确认）」，并在响应未到前保持禁用"…"态防闪烁；`好友申请.html` 搜索结果已正确消费 `isFriend`（该文件 104 行显示灰色「已是好友」，可按 A4 改为「发消息」）。

### A-⑤ 「设置页『修改密码』不可用」 —— ✅ 成立（前端占位 + 后端无接口，功能完全缺失）

- **复现步骤**：登录在线态打开 `设置.html` → 点击「🔑 修改密码」→ 捕获 toast。
- **实测结果**：`stIsOnline() === true`，点击后 toast = **「ℹ️ 在线账号修改密码需后端接口支持（【后续扩展点】）」**，随后无任何表单/请求。
- **证据 / 根因**：
  - 前端：`设置.html:1033-1034`
    ```js
    function stChangePassword() {
      if (stIsOnline()) { showToast('ℹ️ 在线账号修改密码需后端接口支持（【后续扩展点】）'); return; }
    ```
    （仅离线本地账号 `study_workbench_users` 分支可用，1035-1051 行）
  - 后端：`server/routers/auth.py` **只有** `POST /register`(32)、`POST /login`(53)、`POST /refresh`(61)、`GET /me`(73) —— **没有任何改密接口**；`users.password_hash` 字段虽存在（`hash_password/verify_password`）可直接复用。
  - FAQ 也自认：「密码忘记了怎么找回？…请联系管理员在服务器端重置」（`设置.html:432-433`）。
- **严重度**：**中高**（在线用户唯一改密途径不存在；`stDeleteAccount()` 注销在线账号同样直接 return，`设置.html:1054`）。
- **建议修法**：按 PRD-A6 —— 后端新增 `POST /api/auth/change-password`（登录态 + 校验 oldPassword + `hash_password` 落库 + `rate_limit`）；前端 `stChangePassword()` 在线分支改为弹窗表单（当前/新/确认 ≥6 位），本地分支保留。
