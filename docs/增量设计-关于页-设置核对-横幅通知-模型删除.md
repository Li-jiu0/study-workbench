# 需求 C · 横幅通知修复（定位结论 + 修复设计 + 验证清单）⚠ 需重打包

## C.1 定位结论（按嫌疑度排序，附文件:行号证据）

**嫌疑 1（最高）：Android 13+ `POST_NOTIFICATIONS` 运行时权限被拒且无引导闭环。**
- 拒绝即静默：`MsgPollService.java:355-358`——notifyMessage 前置检查，未授权直接 `return`（服务照常轮询、就是不弹）；
- 申请只做一次且无兜底：`MainActivity.java:128`（onCreate → maybeRequestNotifyPermission）、`:1748-1755`；授权结果分支 `:2000-2009`——**拒绝分支无任何 toast/跳系统设置/二次引导**（对比定位权限 :2015-2017 是有 toast 引导的）；
- 症状吻合度：前台「正常」其实是**页面 JS 应用内提醒**（window.xtNotifyMessage / AndroidBridge.notify），完全不依赖系统通知权限——用户看到的正是「仅应用内提醒」。一旦用户在首启弹窗点了「不允许」（或 ROM 静默拒绝），后台横幅永久静默。

**嫌疑 2：进程被杀/划掉后台后，前台服务恢复不可靠（国产 ROM 尤甚）。**
- `MsgPollService.java:53-54` 自述「彻底划掉后台/被系统回收后重新拉起依赖 START_STICKY，真机 ROM 差异较大」；`onStartCommand:126` 返回 START_STICKY，null intent 时读 SharedPreferences 恢复（:112-117、:197-208）——逻辑本身正确，但 **START_STICKY 的重启时机由系统决定**，MIUI/EMUI/ColorOS 划卡后常常不重启或不及时；
- 全项目无 JobScheduler/WorkManager/AlarmManager 兜底拉活（grep 证实）；`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 仅有桥 `requestIgnoreBatteryOptimizations`（MainActivity.java:277-284），**无自动/首启引导调用**——电池优化白名单是否开启完全随缘。

**嫌疑 3：通知渠道跨版本持久化，importance 可能历史性偏低或被用户关渠道。**
- `ensureChannels`（MsgPollService.java:305-324）仅在渠道不存在时创建 `xt_msg`（IMPORTANCE_HIGH，:319）。**渠道设置跨安装保留且程序无法升级 importance**：若设备上残留过旧版本创建的低 importance 渠道（或用户手动关了该渠道的悬浮通知），新版本代码永远无法修正——无自检、无跳渠道设置引导。

**嫌疑 4（放大器）：熄屏 300s 轮询 + Doze。**
- `PollLogic.java:25` 灭屏间隔 300s；Doze 下后台应用网络受进一步限制且无电池豁免 → 熄屏时横幅延迟可达数分钟甚至整夜。非「收不到」根因，但显著恶化体验。

**排除项（实读确认无问题，勿重复排查）**：
- Manifest 声明齐全：POST_NOTIFICATIONS(:17)、FOREGROUND_SERVICE(:19-21)、RECEIVE_BOOT_COMPLETED(:30)、MsgPollService 声明(:68-71)、BootReceiver(:82-88)；
- 前后台判断正确：onResume/onPause 同步 `MsgPollService.appForeground`（MainActivity.java:2053-2064），前台让位页面 JS 不重复弹（MsgPollService.java:294）；
- 进程重启轮询恢复：START_STICKY null-intent 路径读 prefs（:112-127）+ App 启动双保险 ensureMsgPollService（MainActivity.java:2174-2185）+ BootReceiver 开机拉活；
- 点击跳会话深链已有（notifyMessage :363-374 → handleOpenConversation :2140-2170）。

## C.2 修复设计（三态全覆盖）

1. **权限引导闭环（治嫌疑 1）**
   - `MainActivity.onRequestPermissionsResult` REQ_NOTIFY_PERM 拒绝分支（:2000 后）：toast「未开启通知权限，收不到新消息横幅，点击去开启」+ 跳 `Settings.ACTION_APP_NOTIFICATION_SETTINGS`（包名 extra）；

   - `maybeRequestNotifyPermission` 保持首启申请不变。
2. **渠道自愈（治嫌疑 3）**
   - `MSG_CHANNEL_ID` 改 `xt_msg_v2`（旧 xt_msg 遗留不动；新渠道强制 IMPORTANCE_HIGH + 崛起横幅默认）——一次性绕开历史渠道状态；
   - `ensureChannels` 增加自检：`nm.getNotificationChannel(id).getImportance() < IMPORTANCE_HIGH` 时打观测日志（不含坐标/内容）。
3. **拉活兜底（治嫌疑 2）**
   - 新增 `PollKeepAliveJobService`（`android.app.job.JobService`，零依赖；`JobInfo.Builder(…).setPeriodic(15min).setPersisted(true).setMinimumLatency` 兜底），`onStartJob` 里检查 MsgPollService 是否 running（静态标志），未跑则 startForegroundService 拉起；
   - Manifest 注册 service（`permission="android.permission.BIND_JOB_SERVICE"`）+ `setPersisted` 依赖的 RECEIVE_BOOT_COMPLETED 已具备（:30）；
   - 首启（或前端 boot 桥）自动调一次 `requestIgnoreBatteryOptimizations`（桥已存在 MainActivity:277，只接调用），系统弹窗由用户确认，不强制。
4. **熄屏节奏（治嫌疑 4，可选）**：`PollLogic.INTERVAL_SCREEN_OFF_MS` 300s→120s（耗电增量可接受，通知时效↑）；保留 60s 亮屏。
5. **收尾**：`MainActivity.onDestroy` 补 `MsgPollService.appForeground=false`（进程在 Activity 销毁后仍存活时防误判）。
