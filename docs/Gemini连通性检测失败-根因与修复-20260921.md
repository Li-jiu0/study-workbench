# Gemini「连通性检测失败 · Key 无效或已过期」根因与修复

- 报告时间：2026-09-21
- 报障原文：「连通性检测 · Gemini Flash Lite → 检测失败，原因：Google Gemini 的 Key 无效或已过期，请到设置页填写自己的 Google Gemini Key」，并怀疑「是不是把 Gemini 密钥从前端删除了」
- 结论一句话：**没有删除任何密钥**；真正原因是一处 **R131 的遗留半成品**——gemini 的 `apiKey` 字段只把值换成了作废占位串、**字段本身没删**，导致前端一直拿这个作废串直连 Google。

---

## 一、先排除「密钥被删」这个怀疑（证据）

1. `git diff` 对本次会话全部工作区改动做关键词扫描（`gemini/Gemini/GEMINI/user_key/userKey/localStorage.clear/removeItem`）：
   **代码文件 0 命中**——只有 2 行命中，是我写进 `AI模型对接文档.md` 的说明文字。本次会话未碰任何密钥相关代码。
2. `assets/ai-config.js` 的 7 个 provider 现状：

| provider | `apiKey` 字段 |
|---|---|
| zhipu / qianfan / ark / arkimage / openrouter / siliconflow | **不存在**（R131 已整行删除） |
| **gemini** | **仍存在**，值为 `AQ.***REDACTED-已泄露作废-需换新KEY***` |

→ 也就是说：**别的 6 家删干净了，只有 gemini 落下了**。这正是故障来源。

---

## 二、真根因

`assets/ai-service.js` 的 `xtResolveChannel()`（通道判定唯一真源）里有一句：

```js
var provKey = (provider && typeof provider.apiKey === "string" && provider.apiKey) ? provider.apiKey : "";
if (provKey) return { relay: false, key: provKey, from: "provider" };
```

**它只判断这个值「非空」，不判断它是否有效。** 于是：

```
providers.gemini.apiKey = "AQ.***REDACTED...***"   ← 非空
        ↓
xtResolveChannel(gm-flash-lite) → { relay:false, from:"provider" }   ← 绕过服务端中转
        ↓
拿作废串直接请求 generativelanguage.googleapis.com
        ↓
Google 返回 401 / 403
        ↓
classifyHealthErr → "http_401"
        ↓
ai-settings.js:966 → 「Google Gemini 的 Key 无效或已过期，请到设置页填写自己的 Google Gemini Key」
```

调用链逐行核对（`aiHealthCheckImpl`）：

| 行 | 代码 | 结果 |
|---|---|---|
| 3750 | `var eff = resolveEffectiveEndpointKey(ping);`（内部调 `xtResolveChannel`） | `relay=false`, `apiKey="<作废串>"` |
| 3752 | `if (!eff.apiKey && !eff.relay)` | 不命中（作废串非空） |
| 3776 | `if (eff.relay)`（走服务端中转分支） | **不命中**（relay=false） |
| — | 落到前端直连探测 | → 401 |

**这个报错文案把人引向错误方向**：它让用户去「填自己的 Key」，而真正的问题是内置占位串。

## 二·补 关键补充：你在设置页填的那个 Key 没有被删，但它当时**根本没被用上**

这是「看起来像是我把你前端的 Key 删了」的真正原因——**不是被删，是被内置占位串抢先顶掉了**。

`xtResolveChannel()` 的判定顺序（源码 972–989 行）：

```js
973  var own = (mc.apiKey ...) ? mc.apiKey : "";          // ① 模型级 Key
974  if (own) return { relay:false, key:own, from:"model" };
978  var provKey = provider.apiKey ... ;                   // ② 内置平台 Key ← 修复前 gemini 是占位串（非空！）
979  if (provKey) return { relay:false, key:provKey, from:"provider" };   ← 在这里就 return 了
980  var uk = xtUserOwnKey(mc);                            // ③ 用户自备 Key（localStorage ai_user_key_gemini）
981  if (uk) { ... byokKey: uk ... }                       ← 永远走不到
```

**② 排在 ③ 前面**，而 ② 在修复前恒为非空（占位串）→ **③ 是死代码，你在设置页填的 Key 从来没机会被读取。**

用测试固化下来的反事实对照（`tools/_r11g_gemini_channel_check.js` 用例 F）：

| 场景 | `xtResolveChannel()` 返回 | 实际发出去的 Key |
|---|---|---|
| **修复前**（`providers.gemini.apiKey` = 占位串 + 你存了自备 Key） | `{relay:false, key:"AQ.***REDACTED-已泄露作废-需换新KEY***", from:"provider"}` | **内置占位串**（`byokKey` 为 `undefined` → 自备 Key 完全被忽略） |
| **修复后**（同一份你存的 Key） | `{relay:true, key:"", from:"builtin", byokKey:"<你的 Key>", byokProvider:"gemini"}` | 先走服务端中转；中转网络类失败时**才**用你的 Key 一次性直连回退 |

所以故障现场是：**你填了 Key → 前端没读它 → 拿内置占位串去连 Google → 401 → 弹窗告诉你「你的 Key 无效，请去填写」**。
（弹窗让你去填一个你早就填过的 Key，这就是整件事最迷惑的地方。）

### 你的 Key 现在还在不在？怎么自查

`ai_user_key_gemini` 没有任何自动清除逻辑——全站扫描确认唯一的两个清除入口都**必须用户手动点按钮 + 二次确认**：

- 模型编辑页的「**清除本机密钥**」按钮（`ai-settings.js:2812 clearKeyOverride`）
- 「关于 → 本机密钥」区的「**清除本机保存的全部模型密钥**」按钮（`ai-settings.js:3303` 起，带确认弹窗）

自查方法：**设置 → AI 模型 → 编辑任意 Gemini 模型**，看密钥行文案：

| 显示 | 含义 |
|---|---|
| `已保存该平台自备 Key（仅存本机，不会上传；服务端代理不可用时用于本地直连；留空保持不变）` + 「清除本机密钥」按钮 | ✅ Key 还在（`byokKeyExists('gemini')` 为真） |
| `内置平台 · 可选填自己的 Key（…）`（无「清除」按钮） | ❌ 本机确实没有存 Key |

如果它显示「已保存」→ Key 一直在，只是被上面那个 bug 屏蔽了，修复后即恢复生效。
如果显示「未填写」→ 是被上面两个**手动**清除入口之一清掉的（或换机/换浏览器/重装 App 导致本机存储重置），需要重新填一次。

## 三、顺带查出的第二处 bug（前后端契约错位）

修完上面那处后，会发现新症状更隐蔽：检测会显示**「正常」**，但实际用不了。

- 后端 `server/routers/ai.py:list_models` 对国内平台按「已配 Key」过滤（不在列表=不可用），
  但对海外平台 `_OVERSEA_PROVIDERS = ("gemini","openrouter")` 是**恒下发**的，只附一个
  `relayAvailable`（`_oversea_ready` = api_key 且 proxy 双齐，或显式 `<PROVIDER>_ALLOW_DIRECT=1`）。
- 前端注释却写着「gemini / openrouter 会被自动剔除」，`relayProviders()` 也**只取 `{id,name}`、把 `relayAvailable` 丢了**，
  `relayProbeAvailable()` 只看「平台在不在列表里」→ 未就绪也判「正常」（假阳性）。

## 四、修复内容

| 文件 | 改动 |
|---|---|
| `assets/ai-config.js` | 删除 gemini 的 `apiKey` 字段（连同说明注释），与其余 6 家口径一致。**这一步同时让「用户自备 Key」这条路径重新可达**（②不再抢先返回，③才轮得到） |
| `assets/ai-service.js` | ① `relayProviders()` 带出 `relayAvailable`（仅显式 `false` 算未就绪；字段缺失=国内平台=可用）<br>② `relayProbeAvailable()` 命中后先查该标记，`false` → `{ok:false, err:"unavailable"}`<br>③ 修正两处与后端实现不符的过期注释 |

改动面：`ai-service.js` +25 −6（2 处功能性改动 + 注释），未触碰任何其他逻辑。

### 修复后「自备 Key」的完整生效条件（源码 `ai-service.js:3253-3262 xtByokDirectFallback`）

你的 Key 会被用作**一次性的本地直连回退**，需同时满足：

1. 所选模型属于 `gemini` / `openrouter`（`XT_BYOK_PROVIDERS`）；
2. localStorage 里存了 `ai_user_key_gemini`；
3. 「海外平台代理」设置为 **非 `relay`**（`auto` / `direct` 可以；设成 `relay` 则明确要求只走中转，不用你的 Key）；
4. 服务端中转失败且属**网络类**（`kind === "network_limited"` / 超时 / 无 HTTP 状态）。

→ 也就是说：Gemini 走你的自备 Key 时，**你的手机/浏览器必须自己能连上 Google**（自备梯子/代理）。
服务端没配 `GEMINI_PROXY` 时，中转会返回 `network_limited`，随后就会拿你的 Key 直连；
若本机也连不上 Google，最终错误是「自备 Key 直连也失败：本机网络无法直连该海外平台（需代理/梯子），或密钥无效」。

## 六、还需要做的一件事：服务端配置

线上实测 `GET http://110.42.134.62:8000/api/ai/models`：

```
openrouter  →  relayAvailable: true
gemini      →  relayAvailable: false      ← 服务端中转未就绪
```

推论：线上**没有全局 `RELAY_PROXY_URL`**（否则 gemini 也会拿到代理）；openrouter 能就绪靠的是
`OPENROUTER_ALLOW_DIRECT=1`（「服务器实测可直连」的显式 opt-in）。

⇒ **前端修好后，走服务端中转的路径仍连不通**（会如实报「服务端未配置该模型通道 / 服务端网络受限」）。
两条出路，选一条即可：

- **路线 A（推荐，全局生效）**：在服务器 `server/.env` 补
  - `GEMINI_API_KEY=<有效 key>`（本机 `server/.env` 里已配，长度 53）
  - 以及二者之一：
    - `GEMINI_PROXY=<海外代理地址>`（推荐；国内服务器一般直连不通 Google），或
    - `RELAY_PROXY_URL=<海外代理地址>`（对所有海外平台生效），或
    - `GEMINI_ALLOW_DIRECT=1`（**仅当服务器实测能直连** `generativelanguage.googleapis.com` 时才可用）

- **路线 B（本次修复已打通，无需改服务器）**：在设置页填你自己的 Gemini Key，
  并让**本机**能连上 Google（手机挂梯子/代理）。此时链路是
  `先请求服务端中转 → 拿到 network_limited → 自动用你的 Key 本地直连一次`。
  ⚠️ 前置条件：设置页「海外平台代理」不能设成「只走中转(relay)」。
