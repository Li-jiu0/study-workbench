#### ★ B1 关键决策：**必须新增 `last_login_at`，不复用 `last_seen_at`**

理由（3 条，均为源码事实）：

1. **语义不同且会漂移**：`last_seen_at` 在**每一个带 token 的请求**上刷新（`get_current_user` → `_touch_last_seen`，60 秒节流）。用户 12:00 登录、12:30 看一会 → 显示 12:29，与用户要的"上线时刻快照"（"12:00 上线的就显示 12:00"）直接冲突。
2. **复用会污染在线状态**：`online` 由 `ONLINE_THRESHOLD_SECONDS = 5*60` 基于同一字段计算（`users.py:18,29`）。若把登录时刻写进该字段，任何"补写历史登录时间"的动作都会让离线用户被误判在线。
3. **复用无法区分"今天首次上线"**：用户诉求隐含"这次是几点上来的"，只有独立字段能表达"登录动作发生的那一刻"。

**写入时机严格限定**：

| 接口 | 是否写 `last_login_at` | 理由 |
|---|---|---|
| `POST /api/auth/login` | ✅ 写 | 用户主动登录 = 上线动作 |
| `POST /api/auth/register` | ✅ 写 | 注册即首次上线 |
| `POST /api/auth/refresh` | ❌ **不写** | 令牌静默轮换（默认每 60 分钟一次），写了会让"上线时刻"持续漂移回当前时间 |
| `POST /api/auth/change-password` | ❌ 不写 | 非登录动作 |

**显示格式规则**（`formatLastLogin(lastLoginAt, now)`，`now` 可注入便于边界测试）：

| 情形 | 输出 |
|---|---|
| 今天 | `最近登录 12:00` |
| 昨天（跨 1 个自然日） | `最近登录 昨天 22:15` |
| ≥2 天前、同年 | `最近登录 09-10 22:15` |
| ≥2 天前、跨年 | `最近登录 2025-12-31 22:15` |
| 未来时间（客户端时钟偏差） | `最近登录 刚刚`（与 `formatPresence` 同口径，绝不显示未来时间） |
| 空值 / 无法解析 | **返回空串，调用方整行不渲染**（不造假） |

**可见性口径**：`lastLoginAt` 是 presence 白名单（`online`/`lastSeenAt` 同级）的**同级扩展**，与现有口径完全一致（登录用户可查、黑名单双向不可见），**不引入任何新的隐私字段暴露面**；绝不进入 `user_brief`。
